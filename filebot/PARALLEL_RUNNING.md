# 新旧系统并行运行方案

## 概述
本文档描述如何实现新旧系统（smarti → FileBot）的并行运行，确保平滑迁移。

## 并行运行的必要性
1. **业务连续性**：避免服务中断
2. **数据完整性**：确保所有数据正确迁移
3. **功能验证**：验证新系统功能正确性
4. **性能验证**：确保新系统性能满足要求
5. **用户适应**：给用户时间适应新界面

## 并行运行三个阶段

### 阶段一：新系统只读 + 增量迁移（推荐起始点）
**目标**：验证数据迁移正确性和新系统基本功能

**配置**：
- ✅ 旧系统：正常读写
- ✅ 新系统：只读模式
- ✅ 数据流：旧系统 → 增量迁移 → 新系统
- ✅ 用户访问：继续使用旧系统

**验证重点**：
1. 数据迁移准确性
2. 新系统查询功能
3. 性能基准测试
4. 用户界面反馈收集

### 阶段二：新系统读写 + 旧系统只读
**目标**：逐步将用户切换到新系统

**配置**：
- ✅ 旧系统：只读模式（或限制写入）
- ✅ 新系统：正常读写
- ✅ 数据流：旧系统 → 增量迁移 → 新系统
- ✅ 用户访问：逐步切换到新系统

**实施步骤**：
1. 通知用户迁移计划
2. 培训用户使用新系统
3. 分批切换用户组
4. 监控问题和反馈

### 阶段三：完全切换到新系统
**目标**：完成迁移，关闭旧系统

**配置**：
- ✅ 旧系统：关闭或归档
- ✅ 新系统：正常读写
- ✅ 数据流：无（迁移完成）
- ✅ 用户访问：全部使用新系统

**收尾工作**：
1. 最终数据一致性检查
2. 旧系统数据备份
3. 更新文档和培训材料
4. 监控新系统运行状态

## 增量迁移机制

### 迁移频率
- **初始**：全量迁移一次
- **增量**：每5分钟同步一次
- **紧急**：手动触发立即同步

### 同步内容
1. **新增记录**：基于ID或时间戳
2. **修改记录**：基于更新时间戳
3. **删除记录**：软删除标记同步

### 冲突解决策略
**场景1：记录在新系统被修改，旧系统也修改了同一记录**
- 解决方案：以新系统为准，记录冲突日志
- 或：以最后修改时间为准

**场景2：记录在旧系统删除，新系统修改了该记录**
- 解决方案：标记为"已删除"，通知管理员

**场景3：外键关联记录不存在**
- 解决方案：创建占位记录，标记为"待修复"

## 数据一致性验证

### 定期检查脚本
```bash
# 检查记录数一致性
python migration/verify_counts.py

# 检查关键字段一致性  
python migration/verify_data.py --table documents --fields id,title,status

# 检查文件完整性
python migration/verify_files.py
```

### 检查指标
1. **数量一致性**：各表记录数差异 < 0.1%
2. **内容一致性**：关键字段匹配率 > 99.9%
3. **文件完整性**：文件存在且可访问率 > 99.9%
4. **性能指标**：新系统响应时间 < 旧系统150%

## 回滚计划

### 回滚触发条件
1. 数据不一致率 > 1%
2. 关键功能故障无法快速修复
3. 性能不达标（响应时间 > 旧系统200%）
4. 用户投诉率 > 10%

### 回滚步骤
1. **通知**：立即通知所有用户
2. **切换**：将DNS/负载均衡切回旧系统
3. **数据恢复**：如有数据损坏，从备份恢复
4. **问题分析**：分析失败原因，制定改进计划

### 回滚时间目标
- **紧急回滚**：< 15分钟
- **计划回滚**：< 2小时

## 监控和告警

### 关键监控指标
1. **迁移延迟**：数据从旧系统到新系统的延迟
2. **错误率**：迁移失败的记录比例
3. **性能对比**：新旧系统响应时间对比
4. **用户满意度**：用户反馈和投诉率

### 告警阈值
- 迁移延迟 > 30分钟：警告
- 迁移错误率 > 1%：警告
- 迁移错误率 > 5%：严重告警
- 新系统响应时间 > 旧系统200%：警告

## 沟通计划

### 内部团队
1. **技术团队**：每日站会同步进度
2. **运维团队**：监控系统状态
3. **测试团队**：功能验证报告

### 最终用户
1. **迁移前**：通知、培训、FAQ
2. **迁移中**：进度更新、支持渠道
3. **迁移后**：收集反馈、持续优化

|------|------|------|----------|
| 数据迁移失败 | 中 | 高 | 完善回滚方案，分段迁移 |
| 性能不达标 | 中 | 高 | 性能测试优化，容量规划 |
| 功能不完整 | 低 | 中 | 功能对比测试，用户验收测试 |

### 业务风险
| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 用户抵制 | 低 | 中 | 充分沟通，提供培训 |
| 业务中断 | 低 | 高 | 并行运行，逐步切换 |
| 数据丢失 | 很低 | 极高 | 多重备份，数据验证 |

## 时间线建议

### 第1-2周：准备阶段
- 环境搭建，迁移工具开发
- 全量迁移测试
- 性能基准测试

### 第3-4周：并行阶段一
- 新系统只读运行
- 增量迁移验证
- 用户界面测试

### 第5-6周：并行阶段二
- 逐步切换用户
- 监控系统状态
- 收集用户反馈

### 第7-8周：切换完成
- 完全切换到新系统
- 关闭旧系统写入
- 项目总结和文档
